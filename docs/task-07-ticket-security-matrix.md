| درخواست‌کنندهٔ عادی | فقط تیکت‌های خودش + سازمان انتخاب‌شده | ایجاد/مشاهده/پاسخ | غیرقابل دسترسی | نمی‌تواند priority، status، requester، assignee یا visibility را در ساخت تعیین کند |
| عضو دیگر همان سازمان | فهرست خودش؛ جزئیات تیکت دیگری با `404` | فقط تیکت خودش | غیرقابل دسترسی | غیرقابل دسترسی |

## کنترل‌های اجراشده

- درخواست‌کننده و سازمان از JWT/actor و `x-organization-id` معتبر گرفته می‌شوند؛ فیلدهای forged در schemaهای `.strict()` رد می‌شوند.
- list/detail کاربر هم‌زمان روی organization و requester محدودند. detail replyهای `PUBLIC` را در Prisma query انتخاب می‌کند؛ پنهان‌سازی فقط در UI نیست.
- internal note فقط endpoint مستقل محافظت‌شده دارد، با `visibility=INTERNAL` ذخیره می‌شود، notification نمی‌سازد و query کاربر آن را برنمی‌گرداند.
- ساخت تیکت و replyها با `Idempotency-Key` و قید unique سمت DB deduplicate می‌شوند. تغییرات صف UI با `expectedUpdatedAt` از overwrite خاموش جلوگیری می‌کند؛ پاسخ `409` می‌گیرد.
- status transition بررسی می‌شود؛ priority محدود به enum است. جست‌وجو، صفحه‌بندی و فیلترها سمت سرور اجرا می‌شوند.
- RULA/FMEA reference فقط با نوع+شناسهٔ جفت‌شده و موجود در همان organization پذیرفته می‌شود. خطای AI از فهرست allowlist می‌آید؛ raw prompt، provider token یا عکس به تیکت پیوست نمی‌شود.
- audit فقط metadata محدود ثبت می‌کند؛ متن reply/note در audit یا notification قرار نمی‌گیرد. رویداد assignment شناسهٔ اپراتور قبلی/جدید را برای بازسازی تغییر ثبت می‌کند. notification لینک ticket دارد و preview عمومی پیام ندارد.
- دسترسی صف کارکنان تنها با `SUPPORT_OPERATOR_USER_IDS` و `SUPPORT_OPERATOR_ORGANIZATION_IDS` در محیط محافظت‌شدهٔ API فعال می‌شود. هر درخواست صف به یک سازمان جاریِ مجاز محدود است؛ درخواست‌های list/detail و فهرست کارکنان با audit ثبت می‌شوند. متن جست‌وجو، پیام، یادداشت داخلی و محتوای تیکت وارد metadata ممیزی نمی‌شود. اگر هر allowlist خالی/تنظیم‌نشده باشد، مسیرهای کارکنان با `503 SUPPORT_ACCESS_POLICY_UNCONFIGURED` بسته می‌مانند.
- Task 07 attachment تیکت اضافه نکرده است؛ بنابراین upload/download، anti-enumeration و اسکن فایل جدیدی هم ندارد. React متن ticket را به‌صورت متن عادی نمایش می‌دهد و HTML خام نمی‌سازد.

## تصمیم‌های باز برای مالک محصول/حریم خصوصی

1. **دامنهٔ دسترسی بین سازمانی:** دسترسی عمومی `SUPER_ADMIN` حذف شده است. برای هر محیط باید مالک محصول/حریم خصوصی فهرست شناسه‌های اپراتور و سازمان‌های مجاز را تأیید و به‌صورت `SUPPORT_OPERATOR_USER_IDS` و `SUPPORT_OPERATOR_ORGANIZATION_IDS` در secret/config امن سرور ثبت کند. بدون این تصمیم و پیکربندی، صف کارکنان عمداً غیرفعال می‌ماند. این allowlist به‌تنهایی جایگزین بازبینی سیاست نگهداری/حذف نیست.
2. **نگهداری و حذف:** API تیکت route حذف/پالایش یا زمان انقضای retention ندارد؛ FKها نیز `Restrict` هستند. داده مطابق دیتابیس فعلی پایدار می‌ماند. مدت نگهداری و فرایند حذف باید با سیاست حریم خصوصی/حقوقی تعیین شود.
3. **پیوست و ارجاع assessment:** عکس/فایل پیوست پشتیبانی وجود ندارد. ارجاع assessment با ID درون همان سازمان validate می‌شود؛ مالکیت شخصی رکورد ارجاع‌شده در این مسیر validate نمی‌شود. اگر سیاست سازمان فقط اجازهٔ ارجاع رکوردهای خود کاربر را می‌دهد، باید قبل از استفاده تعیین و enforce شود.
4. کلاینت‌های قدیمی PATCH تیکت که `expectedUpdatedAt` نمی‌فرستند با سیاست آخرین‌نویسنده سازگار می‌مانند؛ رابط Task 07 timestamp را می‌فرستد.
