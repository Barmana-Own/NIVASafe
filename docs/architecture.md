# معماری

NIVASafe یک Monorepo مبتنی بر pnpm است:

- `frontend`: رابط React + Vite، RTL و PWA
- `backend`: API مبتنی بر Node.js/Fastify
- `shared/domain`: قواعد محاسبات FMEA و RULA
- `backend/prisma`: مدل و migrationهای MySQL

ساختار canonical پروژه همین مسیرهاست؛ مسیرهای قدیمی `apps/`، `packages/` و
`infrastructure/` که در مخزن قبلی وجود داشتند با این ماژول‌های معادل جایگزین
شده‌اند و برای جلوگیری از اجرای نسخه‌های موازی در شاخه اصلی نگهداری نمی‌شوند.

مرورگر فقط با API ارتباط دارد. API از Prisma برای MySQL استفاده می‌کند و فایل‌ها را در دیسک محلی یا S3-compatible storage نگه می‌دارد. Redis برای صف AI و ایمیل در استقرار production استفاده می‌شود؛ در توسعه محلی عملیات fallback بدون Redis اجرا می‌شوند.

دسترسی مدیریتی دو سطح مجزا دارد: `SUPER_ADMIN` از فضای مدیریتی سراسری `/admin` و endpointهای محافظت‌شده `/admin/*` برای کنترل حساب‌های کاربران در همه سازمان‌ها استفاده می‌کند، در حالی که `ORG_ADMIN` فضای مدیریتی سازمانی `/admin` را با APIهای tenant-isolated اعضا دریافت می‌کند. هر دو سطح از مسیر دعوت امن `/members` می‌توانند مدیر یا دستیار اضافه کنند؛ `ASSISTANT` یک نقش سازمانی محدود برای کارهای عملیاتی، ارزیابی و گزارش است و مجوز مدیریت کاربران یا تنظیمات سازمان را ندارد. کاربران عادی به فضاهای مدیریتی دسترسی ندارند.

ثبت‌نام یک کاربر جدید یک مرز تراکنشی onboarding است: کاربر، فضای کاری اولیه، عضویت `ORG_ADMIN` و یک پروژه `DEFAULT` آماده برای تست FMEA/RULA در یک تراکنش Prisma ساخته می‌شوند. ایجاد سازمان‌های بعدی نیز همین پروژه پیش‌فرض را با نام متناسب با زبان فضای کاری ایجاد می‌کند. برای سازمان‌های قدیمی، خواندن فهرست پروژه‌ها همین پروژه را به‌صورت idempotent و در محدوده همان سازمان backfill می‌کند و در صورت soft-delete شدن آن را فعال برمی‌گرداند؛ شناسه `DEFAULT` در برابر حذف محافظت می‌شود و پروژه مشترک بین سازمان‌ها وجود ندارد.

هر حساب می‌تواند چند سازمان مستقل داشته باشد؛ رابطه‌ی عضویت (`OrganizationMember`) هویت، نقش و فعال‌بودن دسترسی را برای هر سازمان جدا نگه می‌دارد. انتخاب سازمان در پوسته‌ی برنامه فقط از عضویت‌های برگشتی API انجام می‌شود و شناسه‌ی انتخاب‌شده به‌عنوان scope ارسال می‌شود؛ API نقش را دوباره از عضویت همان سازمان استخراج می‌کند. وضعیت، طرح و تاریخ انقضای اشتراک روی خود سازمان نگهداری می‌شود و در production سازمان تازه‌ساخته‌شده تا دریافت نتیجه‌ی واقعی پرداخت در وضعیت `PENDING_PAYMENT` می‌ماند؛ مسیرهای billing و مدیریت سازمان برای تکمیل پرداخت باز هستند، اما مسیرهای عملیاتی با `SUBSCRIPTION_REQUIRED` مسدود می‌شوند.


## هوش مصنوعی

حالت `fallback` همیشه از پایگاه دانش داخلی استفاده می‌کند. با `AI_ENABLED=true` و تنظیم کلید و مدل، آداپتور ArvanCloud AI (سازگار با OpenAI)، OpenAI، Gemini یا Anthropic فعال می‌شوند. مدل و ارائه‌دهنده برای دو نقش مستقل تنظیم می‌شوند: `AI_RISK_PROVIDER` و `AI_RISK_MODEL` برای ارزیابی ریسک، با زنجیره‌ی جایگزین `AI_RISK_FALLBACK_PROVIDER` و `AI_RISK_FALLBACK_MODEL`، و `AI_CHAT_PROVIDER` و `AI_CHAT_MODEL` برای چت. پیکربندی فعلی برای ارزیابی‌ها `GPT-5-Mini` و برای گفت‌وگو `DeepSeek-V4-Flash` است؛ در قطعی مدل ارزیابی، همان مدل fallback و سپس پایگاه دانش داخلی استفاده می‌شود. همه‌ی درخواست‌های HTTP دارای timeout و retry محدود برای خطاهای موقت هستند و در صورت در دسترس نبودن ارائه‌دهنده چت، پاسخ به‌صورت امن به fallback برمی‌گردد.
