# Stage 06 — API Design and Integration

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/v1/fmea/job-catalog?search&limit` | Return active global and current-organization job entries; `limit` is bounded to 200 for the initial client-side catalog load. |
| POST | `/api/v1/fmea/process-suggestions` | With `mode=suggestions`, return catalog/AI process-item suggestions; with `mode=description`, return a bounded description suggestion; with `mode=risk-row`, return bounded failure-mode/effect/cause/recommendation suggestions plus an advisory integer S/O/D score suggestion and rationale; with `mode=job-titles`, preserve the bounded organization-scoped compatibility flow for explicit callers. The live title combobox uses `GET /fmea/job-catalog` and does not invoke this mode. Confirmed assessment fields are not written by suggestion modes. |
| POST | `/api/v1/fmea` | Persist the user's confirmed process information and assessment metadata. |
| GET/PATCH | `/api/v1/fmea/:id` | Read or update an assessment while preserving tenant and catalog checks. |
| POST/PATCH/DELETE | `/api/v1/fmea/:id/items[/:itemId]` | Create, edit or delete a risk row; on create, legacy `rowNumber` and `processStep` are optional and are derived from the parent assessment when omitted; the server recalculates RPN and risk level using VERY_LOW 1–50, LOW 51–100, MEDIUM 101–200, HIGH 201–400 and CRITICAL above 400. |
| GET | `/api/v1/fmea/:id/report?locale=fa or en` | Return the tenant-scoped FMEA header, executive summary, risk distribution, top failure modes, localized fallback suggestions, action register and complete detail rows. The export route uses the same read model for full-report output. |
| POST | `/api/v1/fmea/:id/report/save` | Record an audit-backed report-save event for the current assessment version. |
| GET | `/api/v1/actions?fmeaId=...` | Filter corrective actions by FMEA assessment. Actions may link to a specific `fmeaItemId`. |
| POST/PATCH | `/api/v1/actions[/:id]` | Create or update a corrective action with tenant-validated project/FMEA/FMEA-row links. |
| GET | `/api/v1/reports/{fmea,rula}/:id.{pdf,xlsx,doc,docx}?locale=fa or en` | Export the selected FMEA or RULA report. PDFs are styled, paginated landscape report snapshots; `xlsx` is a styled multi-sheet workbook; `docx` is an editable Office Open XML document. `doc` remains a backward-compatible alias for DOCX. FMEA also accepts `view=final-table` for the site-aligned data table in all three formats. |
| POST/PATCH | `/api/v1/rula[/:id]` | Create or update a RULA assessment with validated activity information, editable Group A/B posture analysis, measurement units, load context and scoring inputs. |
| POST | `/api/v1/rula/posture-image-analysis` | Analyze exactly one authenticated RULA posture image per request; validates image type, signature and 10 MB limit, requires `assessments.create`, is rate-limited, and calls only GapGPT for this explicitly authorized purpose, with no cross-provider fallback. |
| POST | `/api/v1/rula/task-description-suggestion` | Accept only `{ jobTitle, taskDescription, locale }` (bounded to 180/500 characters); generate an editable one/two-sentence activity description using a RULA-specific ergonomic prompt and the configured risk AI provider. Requires authentication and `assessments.create`, is rate-limited, audited without recording the text, records provider token usage when available, disables organization-knowledge retrieval for this request, and never persists or sends posture images/notes. |
| GET | `/api/v1/rula/:id/report` | Return the tenant-scoped RULA result read model: score/risk, main factors, suggested corrective actions, persisted actions and predicted score. |
| POST/PATCH/DELETE | `/api/v1/actions[/:id]` | Create, update or remove corrective actions; RULA actions may carry bounded `rulaImpact` metadata linked to a RULA assessment. |
| POST | `/api/v1/files` with `entityType=RulaAssessment` | Upload an authenticated posture image for an existing RULA assessment; the server validates tenant ownership, image signature and the 10 MB limit, and transactionally enforces at most four active images per assessment. |
| GET | `/api/v1/admin/ai-usage?page&limit&search` | Return provider-reported AI token aggregates per user; `SUPER_ADMIN` sees all users and `ORG_ADMIN` sees only the selected organization. |
| GET | `/api/v1/activity-log?page&limit&search&action&entityType` | Return a bounded Activity Log. Ordinary users receive their own selected-organization and account-level activity; `audit.read` roles receive the selected organization's activity and active-member account events; each row may include FMEA/RULA metadata and provider-reported AI token usage. The legacy `/api/v1/audit` path remains a compatibility alias. |
| PATCH | `/api/v1/admin/users/:id` | Activate/deactivate accounts and update Super Admin-managed profile/global-role fields; account/session safeguards remain server-side. |
| PATCH | `/api/v1/admin/memberships/:id` | Allow only a Super Admin to change an organization membership role or active state while protecting the last active organization administrator. |
| POST | `/api/v1/admin/users/:id/password` | Allow only a Super Admin to set a strong replacement password for another user; the current password is never returned and all target sessions are revoked. |
| POST | `/api/v1/auth/login` | Verify credentials and return the authenticated user with active organization memberships; the frontend persists the first returned organization for initial scope, but never submits a role assignment. |
| GET/POST | `/api/v1/organizations` | List memberships visible to the authenticated account or create a new organization with an `ORG_ADMIN` membership and localized `DEFAULT` project; creation returns the independent subscription state. |
| POST | `/api/v1/projects` | Create a project with an optional initial process/activity bootstrap; the process name and activity title are validated as a pair, and the optional location is persisted on the linked activity in the same transaction. |
| GET/PATCH | `/api/v1/organizations/current` | Read or edit the selected organization identified by the server-validated `x-organization-id` header. |
| GET/POST | `/api/v1/organizations/current/subscription[/checkout]` | Read or activate the selected organization's independent subscription; production checkout requires an external payment adapter, while local simulation is development-only. |
| POST | `/api/v1/auth/register` | Accept the existing personal or organization registration contract; server-side validation normalizes contacts, validates name parts and organization identifiers, creates the user/workspace/membership/default project atomically, and never returns internal validation details to the UI. |

All responses use the existing `{ data: ... }` envelope. Search and item counts are bounded. Suggestion endpoints never write confirmed FMEA process fields; only the create/update endpoints persist values included by the client and validated by the API. The `job-titles` mode is the exception for the job bank: it writes bounded organization-scoped AI title records to `JobCatalog` with duplicate checks and returns those records for inline selection, without linking them to an assessment. Project creation can atomically persist the initial process and linked activity while remaining backward-compatible for callers that omit the bootstrap fields. Custom job titles remain assessment-local (`jobCatalogId=null`) until the user selects an existing catalog entry. Frontend contract verification reports all current frontend paths matched backend routes.

Risk-row mutations require tenant-scoped assessment permissions and item deletion is confirmed in the UI. Risk-row AI score suggestions are constrained to integer values from 1 through 10, parsed server-side, returned as advisory data only and never persisted by the suggestion route. Report and action routes require the same tenant scope and `reports.generate` permission. FMEA full-report Excel keeps the existing SUMMARY/PROCESS/ACTIONS sheets, makes the visible final table the primary FMEA sheet, and preserves the prior extended table in FMEA DATA; RULA keeps its existing worksheet names and section boundaries. Persian sheets are RTL, cell values are wrapped, and table exports preserve distinct control/action lines. Word exports are valid editable Office Open XML packages; `.doc` remains a compatible alias. Workbook responses use the standard spreadsheet content type.

RULA `activityInfo` and `postureAnalysis` are stored separately from the scoring `inputs` JSON and are validated at the API boundary. The activity context includes an optional bounded `postureDescription` for the assessor's notes. Up to four posture images can be uploaded after the assessment is created; each is a tenant-scoped attachment, and the server serializes the per-assessment count check while adding images. The image-analysis route accepts one image per request, so the client sends each selected image independently. Cross-assessment and cross-organization image references are rejected. The API recalculates score/action level from the submitted scoring inputs, so client-side edits cannot make the stored result authoritative without server validation. The report endpoint derives the main factors and bounded suggestions from the persisted posture observations. A corrective action stores only a bounded reduction estimate and affected posture parts; the report sums selected reductions with a score floor/ceiling and labels the result as a prediction.

AI usage is recorded after successful provider calls for risk requests and chat responses. The aggregate endpoint returns counts only, uses bounded pagination/search, and excludes prompt, completion, credential and raw-provider data.

Organization creation is intentionally available with `allowUnsubscribed` so a user can reach the payment surface for a newly provisioned company. The created organization is `TRIALING` only in development; production creation is `PENDING_PAYMENT`, and the normal authenticated route guard blocks all tenant operations that do not explicitly belong to billing or recovery.

Account identifiers support both email and username. `POST /api/v1/auth/login` and `POST /api/v1/auth/forgot-password` accept `identifier` and resolve it as a validated email or username; the legacy `email` field remains accepted for compatibility. Registration accepts an optional username. Organization member requests require either a username or an email, and persist the omitted identifier as null. `GET/POST /api/v1/member-requests` is limited to the selected organization's user-management permission and exposes pending requests to the requester organization. `GET /api/v1/admin/member-requests`, `POST /api/v1/admin/member-requests/:id/approve`, and `POST /api/v1/admin/member-requests/:id/reject` are Super Admin-only; approval requires a strong initial password, requests an email from the Super Admin when a username-only request is approved, creates the active account and membership transactionally, and never returns or stores the plaintext password.

Login and logout write tenant-visible Activity Log events for each active membership. AI chat messages are linked to their persisted `AIUsageRecord` when provider token counts exist; assessment activity rows resolve the current FMEA/RULA title and code for display. The API never returns prompts, model responses, passwords or token credentials through this read model.

The registration UI keeps the existing wizard and adds a visible personal/organization path, organization manager/company/review steps, recoverable non-secret draft fields, field-local validation, and a pending-activation result. New registrations are created inactive and do not receive an automatic login session; a Super Admin must activate the account before sign-in. The organization account email is the responsible user's validated login email in the current data model; the review step repeats all captured company and manager fields before submission.
