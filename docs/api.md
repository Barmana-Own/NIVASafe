# API

Base path: `/api/v1`. Interactive OpenAPI is served at `/docs`. Responses use `{ "data": ... }`; errors use `{ "error": { "code", "message", "requestId" } }`. Protected calls require `Authorization: Bearer <token>` and tenant calls require `x-organization-id`.

Implemented groups: auth, organizations, projects, processes, activities, FMEA, RULA, corrective actions, dashboard, reports, files, knowledge, chat, notifications, Activity Log and health. Pagination parameters are `page`, `limit`, and `search` where supported.

`GET /activity-log` is the user-facing activity timeline. Every authenticated user can read their own selected-organization and account-level sign-in/sign-out, assessment and AI activity. Users with `audit.read` can also read the selected organization's activity and account-level events for its active members. Rows include the actor, timestamp, localized-client-ready category metadata, FMEA/RULA assessment title/code when applicable, and provider-reported AI token totals when usage was recorded. `/audit` remains a compatibility alias and does not bypass these visibility rules.

`POST/PATCH /actions` accepts the optional `rulaId` and `bodySide` (`LEFT`, `RIGHT`, or `BOTH`). A corrective action linked to RULA must include a body side, and the server enforces compatibility with the assessment's side scope. The actions list returns `bodySide` so the UI and reports can identify the anatomical target.

### Project creation

`POST /api/v1/projects` requires `name`; `code` is optional. When omitted or submitted empty, the API generates a unique `PRJ-XXXXXXXXXX` code so existing project references and reports remain stable. The project-management form may also send `initialProcessName` and `initialActivityTitle` together, plus optional `initialActivityLocation`; when supplied, the API creates the project, its initial process and its linked activity in one transaction. Existing callers that omit these fields remain compatible.

### FMEA process information

- `GET /fmea/job-catalog?search=<term>&limit=<1..200>` returns active global and organization-scoped job catalog entries for the searchable process/job field. The FMEA client loads the catalog once when the field opens and filters titles, alternate-language titles, departments and keywords locally. `POST /fmea/job-catalog` validates and stores a user-confirmed unmatched title in the current organization catalog, returning the created entry for immediate selection; a temporary save failure falls back to an assessment-local title without blocking the form.
- `POST /fmea/process-suggestions` accepts a bounded job title, optional project name, department/activity description/special conditions, an optional tenant-scoped project ID, locale and mode (`suggestions`, `description`, `risk-row`, `job-titles` or `autofill`). In `suggestions` mode, AI output is bounded to at most six items per equipment/materials/controls category; the FMEA process-suggestions board requests this mode only through its explicit in-board AI control and keeps the response editable. In `risk-row` mode it also accepts the current process/failure/effect/cause/preventive-control/detection-control/recommendation context and returns bounded `riskSuggestions` arrays for those six editable text fields plus an advisory S/O/D `scoreSuggestion`. The add-row and review clients automatically apply only the first suggestion to empty fields and untouched scores when the FMEA assistant is enabled; existing user input is never overwritten automatically, and every value remains editable. `job-titles` remains a bounded, authenticated compatibility mode for explicit callers; the live job combobox does not call it and uses the database catalog instead. In `autofill` mode a valid project is required and the response includes bounded `autofill` text fields and process suggestion arrays. The client must treat autofill as editable advice; AI job-bank records are not confirmed assessment data and are never linked to an assessment without explicit user selection.
- `POST /fmea/process-image-analysis` accepts an authenticated multipart image plus bounded job/process context. JPG, PNG and WEBP images are signature-checked and limited to 10 MB; the configured image-capable risk provider returns a bounded advisory summary and draft risk rows. The FMEA client can submit up to three images sequentially, starts analysis automatically after selection, de-duplicates merged draft rows and places the returned rows into the editable review list; the user must review them before registration. The image is not retained by the analysis endpoint. FMEA assessment attachments enforce the same three-image limit server-side.
- `POST /fmea` persists the user-confirmed process fields and selected item arrays; the server validates the project, optional catalog entry, item count/length and required one/two-sentence activity description.
- `POST /fmea/:id/items`, `PATCH /fmea/:id/items/:itemId` and `DELETE /fmea/:id/items/:itemId` create, edit and delete FMEA risk rows. On create, legacy `rowNumber` and `processStep` are optional; the API assigns the next row number and derives process/activity context from the parent assessment when they are omitted. S/O/D are validated server-side, RPN and risk level are recalculated by the API, and item mutations require the tenant assessment-update permission.
- `GET /fmea/:id/report` returns the tenant-scoped FMEA report read model with header metadata, executive counts, risk distribution, top failure modes, NIVASafe suggestions, registered actions and full details. `POST /fmea/:id/report/save` records an audit-backed save for the current assessment version.
- `POST /fmea/:id/report/detail-suggestions` accepts `{ "locale": "fa" | "en" }` and returns at least five bounded, editable FMEA risk-row drafts generated from the project/process context and existing rows. Drafts are not persisted; the client must explicitly review and add them through `POST /fmea/:id/items`. The route is rate-limited, tenant-scoped, requires report permission, writes an audit event and records provider token usage when available.
- `POST /fmea/:id/report/action-suggestions` accepts `{ "locale": "fa" | "en" }` and returns bounded corrective actions linked to server-owned FMEA item IDs. The route calls the assessment AI provider (GPT-5-Mini), validates row mappings and output lengths, merges deterministic HSE fallbacks when the provider is unavailable or returns invalid JSON, excludes already registered action titles, and does not persist anything until the user submits an action. The response includes `provider`, `model`, `aiStatus` and `minimum`; it is tenant-scoped, permission-checked, rate-limited, audited and records token usage when reported by the provider.
- Corrective actions accept an optional `fmeaItemId`; the API verifies that the row belongs to the same organization, project and selected FMEA before persisting it. The report action register can update status and progress through the existing action routes.
- `GET /reports/fmea/:id.pdf`, `GET /reports/fmea/:id.xlsx` and `GET /reports/fmea/:id.docx` export the complete FMEA process context and risk register. The `.xlsx` response is a structured Excel workbook and `.docx` is a real Office Open XML Word document. The legacy `.doc` route remains an alias for the DOCX response.
- `POST /rula/:id/report/action-suggestions` accepts `{ "locale": "fa" | "en" }` and returns validated, bounded corrective actions for the saved RULA posture and task context. It uses GPT-5-Mini for assessment requests, forces the server-selected body side, validates related posture parts and score-reduction bounds, merges non-empty deterministic fallbacks, excludes registered action titles, and leaves selection/persistence to the existing corrective-action endpoint. The route is tenant-scoped, permission-checked, rate-limited, audited and token-usage aware.

- `GET /ai/providers` reports available AI adapters, their role-specific configuration and models without exposing credentials. `POST /ai/requests` creates a risk-analysis request and `POST /chat/conversations/:id/messages` generates a scoped assistant response using the authenticated user's organization knowledge and up to six prior messages from that user's conversation. With the current ArvanCloud AI configuration, risk requests use `GPT-5-Mini`, fail over to the configured `GPT-5-Mini` route and then the deterministic knowledge fallback, while chat uses `DeepSeek-V4-Flash` through the server-side `https://api.arvancloudai.ir/v1` endpoint. Transient provider failures are retried within bounded timeout/attempt limits.

## Account, organizations and recovery

- `POST /auth/register` creates the user, their first organization workspace, an `ORG_ADMIN` membership and one localized `DEFAULT` project in a single transaction. Personal registrations receive a personal workspace; organization registrations receive the submitted company details. The initial project is named `پروژه آزمایشی NIVASafe` in Persian or `NIVASafe Demo Project` in English and is ready for FMEA/RULA testing. The selected subscription plan is applied to the new workspace.
- `GET /projects` idempotently backfills the same localized `DEFAULT` starter project for an existing organization that predates this onboarding behavior and restores it if an older build soft-deleted it, then returns only projects belonging to the authenticated organization. The starter project's name and description may be edited, but its `DEFAULT` identity is protected from deletion. There is no shared cross-organization test project.
- `GET/PATCH /profile` reads and updates the display name, email, phone, job title and interface locale (`fa`/`en`). `POST /profile/change-password`, `POST /auth/forgot-password` and `POST /auth/reset-password` handle secure password changes and recovery. Login and password recovery accept either the normalized email or username as `identifier`; the legacy email field remains accepted.
- Phone fields accepted by registration, profile and member endpoints must be Iranian mobile numbers in canonical local format: exactly 11 ASCII digits matching `^09\d{9}$`. Persian and Arabic-Indic digits and common display separators are normalized before validation; international `+98`/`0098` forms are rejected.
- `GET /members`, `PATCH/DELETE /members/:id`, `GET/POST /member-requests` and `POST /invitations` provide member profile editing, role/active-state management, the two-stage organization member provisioning workflow and backward-compatible email invitations. Organization administrators submit member requests with a required username; only `SUPER_ADMIN` can approve/reject a request and set its strong initial password. Self-registration keeps username optional. The assistant role is intentionally bounded to operational project, assessment and report work, and only `SUPER_ADMIN` can grant or change the global super-administrator role.
- `GET /admin/overview`, `GET /admin/users?page&limit&search`, `GET /admin/ai-usage?page&limit&search` and `PATCH /admin/users/:id` are reserved for the administration surfaces. The overview/user-management routes remain `SUPER_ADMIN`-only; AI usage is global for `SUPER_ADMIN` and organization-scoped for `ORG_ADMIN`. The panels expose aggregate user/organization status, safe user profile editing, activation/deactivation, global-role changes and provider-reported AI token usage per user. Passwords are never editable through this surface; deactivation or global-role changes revoke active sessions, and the backend prevents self-lockout and removal of the last active global administrator.
- `GET /organizations` lists all companies for a super administrator and only active memberships for other users. `POST /organizations` creates a separate organization, an `ORG_ADMIN` membership for the authenticated user and a localized `DEFAULT` test project atomically; the requested plan is stored on that organization only. `GET/PATCH /organizations/current` reads or edits the selected company, while `POST /organizations/current/deactivate` deactivates that company and its memberships.
- Company switching is membership-scoped: the frontend persists only an organization ID returned by login, invitation acceptance or `POST /organizations`, and sends it as `x-organization-id`; the backend rejects an ID without an active membership. `PATCH /organizations/:id/status` requires `SUPER_ADMIN` plus a two-step `confirmation` value (`ACTIVATE` or `DEACTIVATE`) and is audited. Inactive organizations are rejected by the backend with `ORGANIZATION_INACTIVE`.
- Each organization has an independent subscription plan, provider, status, expiry and external payment reference. New production organizations start as `PENDING_PAYMENT`; protected tenant routes return `SUBSCRIPTION_REQUIRED` until that specific organization's subscription is usable. Billing routes remain available to that organization's administrator, and local checkout simulation is development-only.

## Files

- `GET /files` returns organization-scoped attachments. Each item includes a derived `reference` object with a localized-client-ready type (`FMEA`, `RULA`, `KNOWLEDGE` or `OTHER`) and, when the linked record still exists in the same organization, its assessment/document title and code.
- `POST /files` accepts approved organization files and optional reference metadata; assessment-linked uploads are validated against the tenant-owned assessment before storage.

## Knowledge base

- `GET /knowledge/quota` returns the organization plan, token usage, remaining quota and maximum attachment size.
- `GET/POST/PATCH/DELETE /knowledge` manages organization documents. A document can be `isGlobal`, targeted with `visibleOrganizationIds`, restricted to `visibleUserIds`, hidden with `visibility`, or marked `aiOnly` (which requires `aiReadable=true`).
- `POST /knowledge/:id/attachments` accepts approved image, Word, PDF, spreadsheet and text files; `GET /knowledge/attachments/:id/download` and `DELETE /knowledge/attachments/:id` provide scoped file access and removal.
- Global documents are managed by `SUPER_ADMIN`; organization and user visibility is enforced in the backend for every list, attachment and AI context query.
