# Stage 07 — Authentication and Authorization

The new catalog and suggestion routes require authentication, an organization scope and `assessments.create`. FMEA create/update routes retain their existing permission checks. Report reads/saves require `reports.generate`; manual corrective actions require `assessments.update`. `ensureJobCatalog` accepts only active global entries or entries owned by the current organization, preventing cross-tenant catalog access and object-level injection through a client-supplied catalog ID. FMEA row links on corrective actions are checked against the same organization/project/assessment before persistence.

AI provider credentials remain server-only. The frontend receives provider/status metadata, never a key. The AI usage endpoint is available only to `SUPER_ADMIN` and `ORG_ADMIN`; global administrators receive global aggregates, while organization administrators are restricted server-side to active members and usage rows for their selected organization. Login stores only the first organization membership returned by the authenticated server response and never submits or self-assigns a role; the existing in-panel company switcher remains membership-checked and server-validated. The login form exposes standard browser password-manager metadata (`username` and `current-password`) and remembers only the email address when the user enables the remember option; passwords are never stored by the application. All accounts continue directly to the panel after authentication.

Registration is validated again at the API boundary: email and phone are normalized and classified before their field-specific validators run, organization-only fields are required server-side, unknown payload properties are rejected, first/last name parts are checked against the shared allowed-character and reserved-name policy, and organization national identifiers are normalized and checksum-validated. The browser uses the same shared contact classifier to identify email versus phone input, normalizes Persian/Arabic digits for mobile values, and reports a mismatched contact type before submission. The existing wizard preserves non-secret fields across Back/Next and displays generic Persian/English failure copy instead of technical backend errors. No client validation is treated as an authorization or persistence boundary.

Multi-company access is derived from `OrganizationMember` on every scoped request. `POST /organizations` creates a new membership for the requesting account and makes that user an `ORG_ADMIN` of the new company; the browser cannot grant itself a role or select an organization outside its session membership list. Organization administrators can edit and manage billing only for the active organization. Subscription checks are applied after membership and role resolution, so one company's active subscription cannot authorize another company's pending or expired workspace.

Authenticated sign-in and sign-out events are written for each active organization membership, and authenticated AI chat responses add a tenant-scoped activity event linked to the assistant message and provider usage record. The Activity Log exposes these events only through the server-derived self, selected-organization, or global Super Admin scope; it never trusts a client-supplied user or organization filter.

The supported organization roles are `ORG_ADMIN` (organization administration), `HSE_MANAGER`, `HSE_SPECIALIST`, `HSE_OFFICER`, `EXTERNAL_AUDITOR`, `PERSONNEL`, `VIEWER`, `ASSISTANT`, and `ASSESSOR`. `HSE_MANAGER` has the least-privilege `users.request` permission to submit member requests, while only `ORG_ADMIN` and `SUPER_ADMIN` can edit or remove existing members. `SUPER_ADMIN` is the global system manager and is not granted through an ordinary organization invite. New self-registered users are inactive until a Super Admin activates them from the central user panel. The same panel can set a strong replacement password for another account and revokes that account's sessions; no administrator can read an existing password and no plaintext password is stored or logged.

The organization member workflow is two-stage: an organization administrator submits the member's required username, email, display name, role and optional contact details; the request is tenant-scoped and remains pending. A Super Admin reviews the request, sets the strong initial password, and atomically provisions an active user plus organization membership. The UI confirms the generated username after approval so the administrator can deliver the username and the password they entered through a secure channel. Members can later change their password from Profile or use username/email password recovery. Usernames are normalized to lowercase, restricted to 3–64 ASCII letters/digits/periods/hyphens/underscores, and checked against reserved names and unique database constraints.
